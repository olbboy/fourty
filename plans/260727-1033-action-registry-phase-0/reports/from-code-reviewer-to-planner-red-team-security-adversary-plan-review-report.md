## Finding 1: Kernel's `effects.audit` type has no channel for `meta` — will fail an existing must-pass test and silently drops the changed-field audit trail

- **Severity:** Critical
- **Location:** Phase 2 ("Chữ ký (nháp...)" §Architecture, `ActionDef.effects.audit`), reproduced verbatim in Phase 3's `contactsCreate` draft
- **Flaw:** Phase 2 declares `audit?: (input: I, out: O) => { key: string; objectId: string } | null;` — no `meta` field, and the callback signature does not receive `ctx`. `audit()`'s real signature (`src/lib/audit.ts:12-16`) takes `opts.meta?: Record<string, unknown>`, and every current call site uses it for two distinct, currently-tested purposes:
  1. `via` tagging — `src/mcp/tools.ts` tags every audit call with `meta: { via: ctx.via ?? "mcp" }` (e.g. lines 179, 351, 383, 424, 517, 585, 692).
  2. Changed-field tracking — `src/app/api/contacts/[id]/route.ts:62` and `src/app/api/companies/[id]/route.ts:56` write `meta: { fields: changed }` on every update.
  Phase 3's draft `contactsCreate.effects.audit` (`audit: (_i, row) => ({ key: "contact.created", objectId: row.id })`) has literally no field to carry either of these.
- **Failure scenario:** `tests/ai-agent.test.ts:123` — `expect(JSON.parse(audits[0].meta).via).toBe("ai")` — is run against `create_contact`, the exact tool Phase 3 migrates, and is in the "must pass unmodified" list (Phase 3 §Non-functional). Implemented as drafted, this test **fails** the moment `create_contact` is pointed at the kernel, because no code path sets `meta.via`. Separately, `contact.updated`'s `meta.fields` (used for audit-trail field-level change tracking, an actual security/compliance artifact) is silently dropped and **no test catches it** — confirmed by grep: `tests/audit-log.test.ts` only asserts `action` name and immutability, never inspects `meta`. This is the worse half: the `via` regression is at least loud (a failing test), but the `fields` regression ships silently and degrades the immutable audit log's forensic value with no CI signal.
- **Evidence:** `plans/.../phase-02-action-kernel.md:100` (audit effect type); `plans/.../phase-03-contacts-migration.md:82` (draft effect with no meta); `src/lib/audit.ts:12-16`; `src/mcp/tools.ts:179,351,383,424,517,585,692`; `src/app/api/contacts/[id]/route.ts:62`; `src/app/api/companies/[id]/route.ts:56`; `tests/ai-agent.test.ts:123`; `tests/audit-log.test.ts` (no `meta` assertions, grep-confirmed).
- **Suggested fix:** Widen the effect signature to `audit?: (input: I, out: O, ctx: ActionContext) => { key: string; objectId: string; meta?: Record<string, unknown> } | null`, and have `execute()` always merge `{ via: ctx.via }` into whatever meta the effect returns. Add this exact regression (`meta.via` + `meta.fields`) as an explicit Phase 2 kernel test before touching contacts.

## Finding 2: Phase 1's canonical `contact.updated` snapshot spec omits `changedFields`, present in the real REST reference implementation — reproduces the exact parity bug the phase exists to fix

- **Severity:** High
- **Location:** Phase 1 §Requirements ("Snapshot gửi vào `dispatchEvent`... khớp REST hiện tại: `snapshot: { ...row, custom: undefined }`")
- **Flaw:** The stated ground truth is incomplete. REST's actual `contact.updated` dispatch is `snapshot: { ...row, custom: undefined, changedFields: changed.join(",") }` — an extra field the spec text never mentions.
- **Failure scenario:** An implementer following Phase 1's literal spec will produce a GraphQL/MCP `contact.updated` event snapshot missing `changedFields`. Any workflow condition keyed on `changedFields` (e.g. "only run if `status` changed") will behave differently depending on which surface triggered it — precisely the class of bug this phase is chartered to eliminate, just moved to a new field. Phase 4's coverage gate (§Architecture) only asserts "same event set, same audit key, same activity type" across surfaces — it never diffs snapshot *shape*, so this divergence has no gate anywhere in the plan to catch it.
- **Evidence:** `plans/.../phase-01-event-parity-fix.md:32-34`; `src/app/api/contacts/[id]/route.ts:64-69` (actual snapshot with `changedFields`); `plans/.../phase-04-consolidation.md:26-31` (coverage gate scope).
- **Suggested fix:** Correct Phase 1's spec text to the real snapshot shape (`{ ...row, custom: undefined, changedFields }`) for `*.updated` events, and add a snapshot-shape equality assertion (not just event-name equality) to `tests/surface-parity.test.ts` for at least one update case.

## Finding 3: No enforced link between an action's declared RBAC `object`/`verb` and what `run()` actually mutates — the kernel trusts self-reported metadata

- **Severity:** High
- **Location:** Phase 2 §Architecture (`ActionDef.object: string`, `run: (input, ctx) => Promise<O>`); Phase 2 Implementation Step 1 (kernel test list)
- **Flaw:** `execute()`'s entire authorization guarantee reduces to `can(role, action.object, action.verb)` — a free-form string the action author writes, checked once at the top of the chain. Nothing verifies `run()` (arbitrary TypeScript with full `db` access, per ADR-017's own architecture) actually touches the table named by `object`. ADR-017's central sales pitch — "the AI path *cannot* bypass RBAC/field-perms/audit, because there is no second path" (ADR-017 §Consequences) — depends entirely on this metadata staying honest, forever, across every future action author (this plan explicitly anticipates ~50+ more actions in Phase 1-3 of the ADR, likely copy-pasted from the `contactsCreate` template).
- **Failure scenario:** A future action (out of this plan's scope, but the pattern this plan establishes) is authored by copying `contacts/create.ts`, declares `object: "contacts"` (copy-paste residue) but its `run()` actually writes to a more sensitive table (e.g. `settings`, `api-keys` — `ADMIN_OBJECTS`, admin-only for every action per `src/lib/permissions.ts:37`). `can("member", "contacts", "create")` returns `true` (CRM object, member has full read+write — `src/lib/permissions.ts:47`), silently granting a non-admin write to an admin-only resource. Phase 2's test list (RBAC-blocks-before-validate, field-perm-blocks, effects order, redact) never tests this class of mismatch; there is no static or runtime check that `object` corresponds to the table(s) `run()` touches.
- **Evidence:** `plans/.../phase-02-action-kernel.md:84-104` (`ActionDef` shape), `:149-158` (test list, no object/run consistency check); `src/lib/permissions.ts:24-33,47` (`CRM_OBJECTS`/`ADMIN_OBJECTS`, `can()`); ADR-017 line "the AI path *cannot* bypass RBAC/field-perms/audit, because there is no second path" (`docs/adr/017-action-registry.md:119-120`).
- **Suggested fix:** At minimum, document this as an explicit known limitation of the "structural" claim in ADR-017 rather than an absolute guarantee. Better: add a lint/test convention (e.g. an integration test per action asserting the actually-touched table name against `object`) before Phase 1 of ADR-017 (companies/deals) adds more authors to this pattern.

## Finding 4: Kernel's single canonical effects order (`activity → audit → rescore → events`) contradicts both ADR-017's own chain diagram and REST's own inconsistent ordering between create and update — no test pins ordering

- **Severity:** Medium
- **Location:** Phase 2 §Requirements (execute() pseudocode); ADR-017 §Context (guard/side-effect chain diagram)
- **Flaw:** ADR-017's context section states the chain as `... → logActivity() → audit() → dispatchEvent() → recompute*Score() → redact()` — rescore *after* dispatch. Phase 1 states the opposite is the real, must-preserve order: `logActivity → audit → recompute* → dispatchEvent`. Phase 2's kernel pseudocode picks `rescore → events`, matching Phase 1's contacts-create reference but **not** matching REST's own update path, which is internally inconsistent: `contacts/[id]/route.ts` runs `recompute(61) → audit(62) → dispatch(64)`, while `contacts/route.ts` (create) runs `audit(83) → recompute(84) → dispatch(86)` — audit and recompute are swapped between the two REST handlers already, before any refactor.
- **Failure scenario:** The kernel enforces one canonical order for both `contacts.create` and `contacts.update`. Migrating `contacts.update` through it necessarily changes the audit-vs-recompute temporal relationship relative to the current REST update handler for one of the two operations, since REST itself uses two different orders. No test in the repo (grep-confirmed for `audit-log.test.ts`) asserts audit-vs-recompute ordering, so this reordering is invisible to the "tests pass unmodified" gate even though it is a real behavior change to when the audit row is written relative to score recomputation — a distinction that matters if a workflow or webhook consumer relies on audit rows reflecting pre- vs post-recompute state.
- **Evidence:** `docs/adr/017-action-registry.md:26-30` (chain diagram); `plans/.../phase-01-event-parity-fix.md:37-38`; `plans/.../phase-02-action-kernel.md:26-37` (kernel pseudocode); `src/app/api/contacts/route.ts:82-86` vs `src/app/api/contacts/[id]/route.ts:61-64` (order swapped between create/update).
- **Suggested fix:** Before drafting the kernel's canonical order, audit and reconcile audit-vs-recompute ordering across all current REST create/update handlers (not just contacts), decide one canonical order explicitly, and note in the plan which existing handler's behavior is being changed and why it's safe.

## Finding 5: Phase 1's cascade-automation risk is framed only as a "self-hoster surprise," not as a gap in the ADR-015 stop-at-write guarantee's scope

- **Severity:** Medium
- **Location:** Phase 1 §Risk Assessment (row "Bật event mới làm workflow đang chạy nổ hàng loạt"); ADR-017 §Explicitly out of scope ("autonomous agents that write without confirmation... ADR-015's stop-at-write loop stands")
- **Flaw:** ADR-015's stop-at-write guarantee gates the *tool call* the AI proposes (e.g. `create_contact` requires human confirmation — verified in `tests/ai-agent.test.ts:97-104`). Phase 1 makes that *same confirmed write* newly capable of triggering an unconfirmed, asynchronous cascade: `dispatchEvent` → `runWorkflowsForEvent` → a `webhook` action that POSTs the full unredacted row (`src/lib/workflows/engine.ts:147-170`, `src/app/api/contacts/[id]/route.ts` snapshot is pre-redact per Phase 1's own explicit requirement) to a workspace-configured URL, or a `create_task`/`update_field` action that mutates further records — all with zero additional confirmation, off the request path. The webhook destination itself is SSRF-checked (`src/lib/net.ts:67-106`), so the destination is not attacker-controlled, but the *content* (attacker-influenceable via whatever text a user pasted into the AI chat that becomes contact fields) now reaches that destination and any downstream `update_field`/`create_task` cascade, for the first time, off an AI-driven creation, without a human ever seeing or confirming the cascade.
- **Failure scenario:** A member with a configured `contact.created → webhook` workflow (workflows are a `CRM_OBJECT`, any `member` may create one — `src/lib/permissions.ts:24-33,47`) previously never had that workflow fire from AI-agent-created contacts (the bug). Post-fix, any human-confirmed AI contact creation now silently exfiltrates the full contact row (all fields, unredacted regardless of the confirming user's field-read permissions) to that webhook. The plan's only mitigation is a CHANGELOG entry — a documentation control, not a behavioral one — and treats this purely as an operator-surprise issue, not as a boundary change to what "stop-at-write" actually protects.
- **Evidence:** `plans/.../phase-01-event-parity-fix.md:152` (risk row, mitigation = CHANGELOG only); `docs/adr/017-action-registry.md:139` (out-of-scope claim about ADR-015); `src/lib/workflows/engine.ts:147-170` (webhook action, unredacted snapshot); `tests/ai-agent.test.ts:97-104` (confirms stop-at-write is per-tool-call only).
- **Suggested fix:** State explicitly in Phase 1/ADR-017 that "stop-at-write" bounds the direct tool call only, not downstream workflow cascades, and consider (as a follow-up, not blocking this phase) a workspace-level setting or audit-log flag distinguishing workflow runs triggered by `via:"ai"`/`via:"mcp"` originating events, so operators can filter/alert on them.
