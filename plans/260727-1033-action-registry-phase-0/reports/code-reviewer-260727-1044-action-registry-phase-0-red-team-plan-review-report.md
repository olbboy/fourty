# Red-team review: Action Registry Phase 0 plan (ADR-017)

Reviewer role: Assumption Destroyer. All findings grep-verified against `main` at review time; no code was changed.

## Finding 1: Hand-rolled zod→JSON-Schema subset excludes constructs used by the very schema Phase 3 plans to reuse
- **Severity:** Critical
- **Location:** Phase 2, section "Requirements" / "zod → JSON Schema" (claimed subset: `z.object`, `z.string` (+`.email()`, `.max()`), `z.number`, `z.boolean`, `z.enum`, `.optional()`, `.nullable()`, `.default()`, `z.record`)
- **Flaw:** `src/lib/validators.ts` uses `.min()` 8 times (every required string AND `dealInput.amount: z.number().min(0)`), `.length(3)` once (`dealInput.currency`), `.partial()` 4 times (`contactPatch`, `companyPatch`, `dealPatch`, `taskPatch` — i.e. every update/patch schema), and `.extend()` once (`taskPatch`). None of these are in the claimed subset.
- **Failure scenario:** Phase 2 step 5 states: "construct outside subset → throw clearly at build time, not silently." Phase 3's own worked example (`phase-03-contacts-migration.md` line 65, `input: contactInput`) directly reuses `contactInput`, whose very first field is `firstName: z.string().min(1).max(120)`. Building the JSON Schema for the first action of the first migrated entity throws immediately, per the kernel's own stated design. This isn't an edge case — it's the mainline path.
- **Evidence:** `src/lib/validators.ts:4,18,21,29,33,36,37,38,47,50,58,63,65,71` (grep count: 8×`.min(`, 4×`.partial(`, 1×`.extend(`, 1×`.length(`); `plan.md` phase-02 line 46-49 (claimed subset); `phase-03-contacts-migration.md:65` (`input: contactInput`).
- **Suggested fix:** Re-scope Phase 2's converter to explicitly include `.min()` (string+number), `.length()`, and `.partial()`/`.extend()` (or special-case `ZodObject.partial()` by walking `.shape` directly, since it's structurally still a plain object). Verify the full actual construct list via `grep -oE '\.[a-zA-Z]+\(' src/lib/validators.ts | sort -u` before finalizing the "~80 line" estimate.

## Finding 2: `effects.audit` type signature cannot express `meta`, which real audit calls already rely on
- **Severity:** Critical
- **Location:** Phase 2, section "Architecture" (`ActionDef.effects.audit: (input, out) => { key: string; objectId: string } | null`)
- **Flaw:** The kernel's audit effect can only produce `key` + `objectId`. The real `audit()` helper accepts an optional `meta` (`src/lib/audit.ts:15`), and existing call sites already depend on it: REST `contact.updated` passes `meta: { fields: changed }` (a diff of which fields actually changed); MCP's `create_contact`/`update_contact`/`delete_contact` pass `meta: { via: ctx.via ?? "mcp" }`.
- **Failure scenario:** Migrating `contacts.update`/`contacts.create` through this effect shape silently drops `meta` from every audit row written via the new path. No existing test asserts on audit `meta` content (`tests/audit-log.test.ts` only checks `entries.some(e => e.action === "contact.created")`), so Phase 3's hard exit bar ("all pre-existing tests pass unmodified") gives a false green light while audit trail fidelity regresses — a trust-boundary/compliance concern, not just an aesthetic one.
- **Evidence:** `phase-02-action-kernel.md:100` (`audit?: (input: I, out: O) => { key: string; objectId: string } | null`); `src/lib/audit.ts:12-16` (real signature has `meta`); `src/app/api/contacts/[id]/route.ts:63` (`meta: { fields: changed }`); `src/mcp/tools.ts:178,351,383` (`meta: { via: ctx.via ?? "mcp" }`).
- **Suggested fix:** Add `meta?: Record<string, unknown>` to the `audit` effect return type before Phase 2's `tests/action-kernel.test.ts` locks the shape in.

## Finding 3: Effects receive only `(input, output)` — no pre-mutation state — but contacts.update already needs a diff against `existing`
- **Severity:** High
- **Location:** Phase 2, section "Architecture" (effects signatures); Phase 3, "Three details that break parity" (list does not mention this)
- **Flaw:** REST `contacts.update` computes `changed = Object.keys(fields).filter(k => fields[k] !== existing[k])` (a diff against the **pre-mutation** row) and uses it for three effects simultaneously: (1) `logActivity` is skipped entirely when `changed.length === 0 && custom === undefined`, (2) `audit()`'s `meta.fields = changed`, (3) the dispatched snapshot carries `changedFields: changed.join(",")`. The kernel's effects signature `(input: I, out: O)` has no parameter carrying `existing`/pre-mutation state, so none of these three effects can be reproduced faithfully without smuggling extra fields through `run()`'s output (which then risks leaking through `redact()` into the actual API response unless explicitly stripped).
- **Failure scenario:** Phase 2's own kernel test list (step 1) only pins guard order, effect order, and a run-throws-no-effects case on a synthetic single action — it never exercises an "update with field diff" scenario. This gap is invisible until Phase 3 wires up `contacts.update`, at which point either the kernel's effect signature must be redesigned (violating Phase 2's "locked" exit) or the diff logic gets duplicated ad hoc inside `run()`, defeating the stated purpose of centralizing effects.
- **Evidence:** `src/app/api/contacts/[id]/route.ts:37-63` (compute+use of `changed` in three places); `phase-02-action-kernel.md:98-104` (effects signature, no `existing` param); `phase-02-action-kernel.md:149-157` (kernel test list has no diff-based scenario).
- **Suggested fix:** Either pass `existing`/pre-mutation state into effects (`(input, out, prev) => ...`), or require `run()` to return a structured `{ output, activityMeta, auditMeta, changedFields }` envelope that the kernel explicitly unpacks (and strips before redact/serialize). Decide before Phase 2 exit, not during Phase 3.

## Finding 4: `contacts.delete` has real, un-inventoried three-way behavioral divergence — Phase 3 will very likely hit its own "stop and report" trigger
- **Severity:** Critical
- **Location:** Phase 3, "Three chi tiết dễ làm hỏng parity" (list covers only `ownerId`, `custom` merge, list-redact — omits delete entirely)
- **Flaw:** Two independent, verified divergences in "delete a nonexistent contact" and "delete cascade":
  1. **Not-found handling:** REST returns HTTP 404 with `apiError("Contact not found", 404)` (`src/app/api/contacts/[id]/route.ts`); MCP throws `ToolError("Contact not found")` (`src/mcp/tools.ts:372`); GraphQL's `deleteContact` silently returns `false` with no error at all (`src/lib/graphql/schema.ts:440`, `if (!existing) return false;`).
  2. **Cascade cleanup:** REST and MCP both delete related `notes` and `activities` rows after deleting the contact (`src/app/api/contacts/[id]/route.ts` DELETE handler; `src/mcp/tools.ts:380-382`). GraphQL's `deleteContact` (`src/lib/graphql/schema.ts:434-444`) does **not** — and there is no DB-level cascade to compensate: `notes.entityId`/`activities.entityId` are plain `text` columns with no FK (`src/db/schema.ts:279-306`), so GraphQL-deleted contacts leave permanently orphaned notes/activities.
- **Failure scenario:** Unifying `contacts.delete` into one `run()` necessarily changes at least two of the three surfaces' observable behavior (GraphQL must start throwing/cascading, or REST/MCP must stop). Phase 3's own architecture section says: "if [a divergence] is found → stop, report user; don't silently pick a side." This is a second (in fact two) undocumented divergence of exactly that kind, discovered — by this review, not by the plan's own step 2 diff exercise — before Phase 3 even starts. The phase's effort estimate ("M") and success criteria assume delete is one of the "easy" ops; it is not.
- **Evidence:** `src/app/api/contacts/[id]/route.ts:69-82`; `src/mcp/tools.ts:367-385`; `src/lib/graphql/schema.ts:434-445`; `src/db/schema.ts:279-306` (no FK on `entityId`).
- **Suggested fix:** Treat this as a Phase-1-style behavior fix (separate from structural refactor), decided explicitly with the user before Phase 3 touches `contacts.delete`: pick one not-found contract and one cascade behavior, document as a deliberate change, add to `CHANGELOG.md` alongside the dispatchEvent fix.

## Finding 5: `logActivity` divergence on `contacts.update` is real, verified, and untracked by the plan's bug matrix
- **Severity:** High
- **Location:** plan.md, "Bug đang tồn tại" (matrix tracks only `dispatchEvent`); Phase 1 scope (fixes only `dispatchEvent` gaps)
- **Flaw:** For the identical operation "update a contact," `logActivity` behavior differs on all three surfaces: REST logs conditionally, only when `changed.length > 0 || custom !== undefined`, with `meta: { fields: changed }` (`src/app/api/contacts/[id]/route.ts:49-55`); MCP logs **unconditionally** on every call, with no diff computation and no `meta` at all (`src/mcp/tools.ts:350`); GraphQL's `updateContact` resolver calls `logActivity` **zero times** (`src/lib/graphql/schema.ts:411-430` — no `logActivity` import use in this resolver at all).
- **Failure scenario:** Plan.md's matrix and Phase 1's fix list are scoped strictly to `dispatchEvent`. This `logActivity` divergence is not mentioned anywhere in the plan, so Phase 1 will not fix it, and it surfaces fresh during Phase 3 (a phase whose hard exit criterion is *zero* behavior change) — the same class of problem as Finding 4, compounding the risk that Phase 3 cannot actually stay behavior-neutral for `contacts.update`.
- **Evidence:** `src/app/api/contacts/[id]/route.ts:49-55`; `src/mcp/tools.ts:350`; `src/lib/graphql/schema.ts:411-430` (absence confirmed by grep — no `logActivity` in the file's `updateContact` block).
- **Suggested fix:** Extend Phase 1's parity fix (and `tests/surface-parity.test.ts`) to cover `logActivity` calls, not just `dispatchEvent`, before declaring the event matrix "fixed" and treating Phase 3 as a pure refactor.

## Finding 6: Plan.md's own "no contract change" constraint contradicts Phase 2's resolved design decision for MCP `list_contacts`
- **Severity:** Medium
- **Location:** plan.md, "Ràng buộc thiết kế" #5 ("MCP `tools/list` output phải giống hệt trước/sau Phase 3") vs. Phase 2, "Quyết định chốt tại đây" #2
- **Flaw:** Phase 2 explicitly resolves an open question by deciding query params (`?q=`, `?sort=`, `?limit=`) belong in the action's `input` schema specifically **so that** "MCP `list_contacts` cũng lọc/sắp xếp được" — i.e., deliberately widening `list_contacts`'s capability to add filter/sort params it does not have today. Plan.md's own hard constraint #5, however, demands the MCP `tools/list` output be **identical** ("giống hệt") before and after Phase 3. Phase 3's success criteria then quietly downgrades the bar to "tương thích" (compatible) for MCP tool schema specifically, without flagging that this conflicts with the plan-level constraint.
- **Failure scenario:** Whoever reviews Phase 4 against plan.md's acceptance criteria ("MCP `tools/list` output phải giống hệt trước/sau Phase 3" is never itself amended) will find the criterion technically violated by design, with no recorded decision reconciling it — a documentation/governance gap that surfaces at sign-off, not during implementation.
- **Evidence:** `plan.md:75-76` (constraint #5); `phase-02-action-kernel.md:112-116` (Q2 resolution, explicit "một cái lợi cụ thể"); `phase-03-contacts-migration.md:30` ("tương thích với hiện tại" — weaker language, no cross-reference to the conflict).
- **Suggested fix:** Reconcile explicitly: either amend constraint #5 to "backward-compatible superset" for MCP input schemas, or exclude `list_contacts`' new filter/sort params from Phase 3 and defer them.

## Finding 7: REST vs MCP/GraphQL blocked-write error text differs; existing tests are too loose to catch drift either way
- **Severity:** Medium
- **Location:** Phase 2, "Lỗi được ánh xạ đúng ngữ cảnh" (error mapping section, only categorizes by HTTP-status/code family, not by exact text)
- **Flaw:** REST's field-permission-blocked-write message is `Not permitted to set field(s): ${blocked.join(", ")}` (`src/lib/api.ts` via `apiError`, used at `src/app/api/contacts/route.ts:67`). MCP's and GraphQL's equivalent message is `Forbidden: cannot write ${object} field(s): ${blocked.join(", ")}` (`src/mcp/tools.ts:68`, `src/lib/graphql/schema.ts:116`) — a structurally different sentence, not just a formatting nuance.
- **Failure scenario:** `tests/field-permissions.test.ts:107` and `tests/mcp.test.ts:157` both assert only `toMatch(/status/)` — a loose regex that passes regardless of which of the two message formats is used. If the kernel unifies to a single canonical message (likely the MCP/GraphQL style, since it is shared by two of three surfaces already), REST's public error text silently changes for any real API consumer parsing it, while "all pre-existing tests pass unmodified" stays true. This directly undermines the plan's core validation premise that unmodified-tests-passing proves no contract change.
- **Evidence:** `src/lib/api.ts` (`apiError` call site) and `src/app/api/contacts/route.ts:67`; `src/mcp/tools.ts:68`; `src/lib/graphql/schema.ts:116`; `tests/field-permissions.test.ts:107`; `tests/mcp.test.ts:157`.
- **Suggested fix:** Add an explicit exact-string assertion for at least one canonical error message per surface before Phase 3, so the "unmodified tests" bar actually has teeth for text-level contract stability, not just status-code-level.

## Finding 8: MCP `list_contacts` is already materially narrower than REST — a real divergence Phase 3 doesn't inventory
- **Severity:** Medium
- **Location:** Phase 3, "Three chi tiết dễ làm hỏng parity" (list omits this)
- **Flaw:** REST `GET /api/contacts` supports `q` (matches firstName+lastName+email+jobTitle), `status`, `companyId` filters, `sort` (`score`/`name`/`createdAt`/`updatedAt`), default limit 200/max 500 (`src/app/api/contacts/route.ts:13-19`). MCP `list_contacts` supports only `query` (matches firstName+lastName+email — no jobTitle), no `status`/`companyId` filter, no `sort` (hardcoded `updatedAt desc`), default limit 50/max 200 (`src/mcp/tools.ts:120-144`).
- **Failure scenario:** This is a real, pre-existing capability gap, not called out anywhere in Phase 3's enumerated "three details," which creates a false impression that the manual diff-and-classify step (Phase 3 step 2) is a formality rather than the load-bearing discovery step it actually needs to be for `list`.
- **Evidence:** `src/app/api/contacts/route.ts:13-52`; `src/mcp/tools.ts:120-144`.
- **Suggested fix:** Explicitly add `list_contacts` query-capability gap to Phase 3 step 2's diff table so it's classified (deliberate vs. drift) before the action is written, consistent with the plan's own discipline for `ownerId`/custom-merge/redact.
