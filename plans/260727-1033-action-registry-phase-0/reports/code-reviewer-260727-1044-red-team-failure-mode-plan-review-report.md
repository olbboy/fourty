## Finding 1: Behavior flip with no kill switch, mitigated only by a CHANGELOG sentence
- **Severity:** Critical
- **Location:** Phase 1, Risk Assessment row "Bật event mới làm workflow đang chạy nổ hàng loạt"
- **Flaw:** Phase 1 turns on `dispatchEvent` for MCP `create_contact/update_contact/create_task/update_task`, `create_company`, and GraphQL `updateContact/createCompany` — paths that have **never fired workflows before** on any self-hosted instance. The only stated mitigation is "ghi vào CHANGELOG.md" (and that CHANGELOG entry is deferred all the way to **Phase 4**, not Phase 1 where the behavior actually ships).
- **Failure scenario:** A self-hosted operator has a workflow "on `contact.created` → post to Slack webhook + create a follow-up task", built and tested only against manual/REST contact creation. They upgrade past Phase 1. Every AI-agent-imported contact, every MCP-client-created contact, and every GraphQL-created/updated contact now silently starts firing that workflow — duplicate Slack messages, duplicate tasks, unexpected `webhook.deliver` jobs POSTing entity data to a third-party endpoint the operator did not expect to receive AI-sourced records. There is no feature flag, no dry-run mode, no staged rollout, and (per the plan's own phase ordering) no changelog warning exists until Phase 4 ships — i.e. the behavior change can ship and run in production for the entire Phase 2-3 window with zero operator-facing warning.
- **Evidence:** `plans/.../phase-01-event-parity-fix.md:152` (risk row, mitigation = CHANGELOG only); `plans/.../phase-04-consolidation.md:99-102` (CHANGELOG entry is a Phase 4 deliverable, not Phase 1); `src/mcp/tools.ts:160-179` (create_contact handler, confirmed no dispatch today).
- **Suggested fix:** Write the CHANGELOG/behavior-change entry as part of Phase 1's own commit (not deferred to Phase 4), and add an explicit, documented env toggle (e.g. `WORKFLOW_DISPATCH_SURFACES` or simply "disable all workflows before upgrading, re-enable after review") to the Phase 1 deliverable so operators can audit workflow configs before the new dispatch paths go live.

## Finding 2: Recursion-guard check is a risk-table footnote, not a gating step — and the guard doesn't exist
- **Severity:** Critical
- **Location:** Phase 1, Risk Assessment row "Vòng lặp vô hạn"; Implementation Steps (1-7)
- **Flaw:** The plan's own text says: *"Nếu thiếu cơ chế chống, dừng và báo user — vượt phạm vi phase này."* This is a blocking condition. But it lives only inside a risk-table cell — none of the 7 numbered Implementation Steps require actually performing this check before proceeding. Verification confirms the guard is in fact absent: `runAction()` (`src/lib/workflows/engine.ts:84-193`) has no depth counter, no re-entrancy flag, no dispatch-chain tracking. It happens to not recurse today only because the fixed `WorkflowAction` union (`create_task`, `add_note`, `update_field`, `webhook`, `log`, `ai_draft`) never calls `dispatchEvent` itself — an incidental property of the current action catalogue, not an enforced invariant.
- **Failure scenario:** Per the plan's own stated exit criterion, this should already be a stop-and-report condition today (the guard is missing). Because it's not wired into the numbered steps, an implementer following the checklist literally will complete Phase 1 without ever running this check. If a future change (in-scope for later ADR-017 phases, but reachable by anyone extending `WorkflowAction`) adds an action type that mutates through the kernel/REST path instead of raw `db.*` calls, the "incidental non-recursion" property silently disappears with no test catching it.
- **Evidence:** `plans/.../phase-01-event-parity-fix.md:153` (risk cell only); `plans/.../phase-01-event-parity-fix.md:100-125` (Implementation Steps, no recursion-check step); `src/lib/workflows/engine.ts:84-193` (`runAction`, no dispatch/recursion tracking).
- **Suggested fix:** Move the recursion-guard verification into Implementation Steps as its own numbered, checkable step (e.g. step 1.5: "grep confirm `runAction` never calls `dispatchEvent`; add a regression test asserting this invariant"), not a risk-table aside.

## Finding 3: Rollback story is only true before Phase 4 ships; the plan doesn't say what happens after
- **Severity:** Critical
- **Location:** plan.md §Rollback; Phase 3 §Architecture "Strangler"; Phase 4 §Requirements "Xoá code chết"
- **Flaw:** `plan.md:103-105` states: *"Phase 3 rủi ro nhất: adapter và code cũ sống song song tới Phase 4, nên revert Phase 3 chỉ là đổi import ... về đường cũ."* This is true only while the old handler/resolver/tool code still physically exists in the tree. Phase 4's own Requirements explicitly delete that code (`phase-04-consolidation.md:23-25`, "Xoá đường code cũ của contacts còn sót lại"). Once Phase 4 has merged, "swap the import back" is not a revert — the code it would point to no longer exists.
- **Failure scenario:** Phase 3 and Phase 4 both ship. Weeks later, a subtle contacts-kernel bug surfaces in production (e.g. the `custom`-merge or list-redact edge case Phase 3 itself flags as high-risk). The on-call engineer reads the plan's Rollback section, expects "just swap the import," and finds the old REST/GraphQL/MCP contact implementations are gone — reverting now requires reverting **two** commits in sequence (the Phase 4 deletion commit, then the Phase 3 migration commit), which the plan never states, and which may not apply cleanly if any other change has landed on those files since (companies/deals routes are adjacent code in the same files: `src/lib/graphql/schema.ts`, `src/mcp/tools.ts`).
- **Evidence:** `plans/260727-1033-action-registry-phase-0/plan.md:101-105`; `plans/.../phase-04-consolidation.md:23-25,56-59`.
- **Suggested fix:** State explicitly in the Rollback section that reverting after Phase 4 requires reverting the Phase 4 deletion commit first, and that Phase 4 should not ship until Phase 3 has run in production for a defined bake period (the plan currently has no bake-period requirement between phases at all).

## Finding 4: The cited test-spy pattern does not exist anywhere in the test suite
- **Severity:** High
- **Location:** Phase 1, §Architecture "Cách bắt event"
- **Flaw:** The plan instructs: *"spy/mock dispatchEvent ... bằng vi.spyOn ... Xem tests/engine.test.ts để lấy pattern có sẵn."* `grep -rn "vi.spyOn" tests/*.ts` returns **zero** matches in the entire repo. `tests/engine.test.ts` does not spy on `dispatchEvent` at all — it dynamically imports the real function and calls it, then asserts on real side effects (task creation), relying on the `inline` queue driver (`NODE_ENV=test` → `queueDriver() === "inline"`, `src/lib/queue.ts:66-68`) to run synchronously. There is no precedent in this codebase for capturing dispatched events via a spy at the module boundary.
- **Failure scenario:** Whoever implements `tests/surface-parity.test.ts` will look for the referenced pattern, not find it, and have to invent a new capture mechanism from scratch mid-phase. Two real risks follow: (a) if they use `vi.spyOn(engineModule, "dispatchEvent")` on a module accessed via named imports (`import { dispatchEvent } from "@/lib/workflows/engine"` — used identically in `contacts/route.ts:7`, `mcp/tools.ts:21`, `graphql/schema.ts:23`), whether the spy intercepts the call depends entirely on Vitest's ESM-to-interop transform behavior, which is unverified here and has no working example in this repo to copy; (b) alternatively, they may fall back to asserting on `workflow_runs` rows — the exact flaky pattern the same paragraph explicitly warns against, without an alternative already proven to work.
- **Evidence:** `grep -rn "vi.spyOn" tests/*.ts` → 0 results; `tests/engine.test.ts:1-45` (real dispatch, no mock); `src/lib/queue.ts:66-68` (inline driver in test env).
- **Suggested fix:** Either build and commit a minimal working spy example against this codebase's actual module resolution before Phase 1 starts (proving the ESM binding is interceptable under this project's Vitest config), or drop the spy approach and design the harness around dependency injection (e.g. an in-memory `EventContext[]` sink passed through `ActionContext`/`ToolContext` for tests only).

## Finding 5: Kernel centralization inherits and amplifies a cross-connection non-atomicity between the request transaction and the enqueued workflow job
- **Severity:** High
- **Location:** Phase 2, §Non-functional "Kernel không mở transaction riêng"; Phase 1, §Non-functional (ordering claim)
- **Flaw:** `dispatchEvent()` in `pgboss` mode calls `boss.send()` (`src/lib/queue.ts:152-161`), which writes to a **separate PgBoss-owned connection pool** (`queueConnectionString()`, owner role, `pgboss` schema — `src/lib/queue.ts:70-77`), entirely outside the calling request's `withWorkspace()` transaction (`baseDb.transaction` in `src/db/index.ts:98-105`, a different pool). That `boss.send()` commits immediately and independently the moment it returns. In every current REST route, `dispatchEvent()` is called **before** the final `redact()` call that builds the JSON response (e.g. `contacts/route.ts:86-93` — `dispatchEvent(...)` then `redact(...)` inside `return json(...)`). If `redact()` (or, in the new kernel, any later effect) throws after `dispatchEvent` has already fired, the outer `withWorkspace` transaction rolls back the entity insert/activity/audit rows — but the already-committed pg-boss job is not rolled back with it, and will later run `runWorkflowsForEvent` against an entity that never persisted.
- **Failure scenario:** A field-permission policy bug or a malformed custom-field payload causes `redact()` (hand-rolled, newly touched by every Phase 2/3 change) to throw for one record. The mutation transaction aborts (contact never exists in the DB), but the previously-enqueued `workflow.dispatch` job is already durable and independent of that rollback. The worker later runs it: `create_task`/`add_note`/`update_field` actions write against `ctx.entityId` for a contact that doesn't exist (orphaned FK-less rows, since these tables don't FK-enforce entity linkage), and `webhook` actions POST a signed payload to an external system describing a "created contact" that was never actually created. This is a pre-existing gap (not introduced by the plan), but Phase 2 formalizes the exact same ordering (`events` before `redact` per the pseudocode in `phase-02-action-kernel.md:26-37`) into a single reusable kernel that every future migrated entity will inherit automatically — and neither phase-01 nor phase-02's risk tables mention it at all.
- **Evidence:** `src/lib/queue.ts:70-77` (separate connection string/role for pg-boss), `src/lib/queue.ts:152-161` (`boss.send()` commits independently), `src/db/index.ts:98-105` (`withWorkspace` uses the app pool's own transaction), `src/app/api/contacts/route.ts:86-93` (dispatch before redact/return today).
- **Suggested fix:** Either move `dispatchEvent`/`effects.events` to run strictly after every other effect including `redact()` has succeeded (so a late throw can't leave an orphaned job), or explicitly document this as an accepted, pre-existing risk in the ADR's Consequences section rather than silently carrying it forward unexamined.

## Finding 6: Phase 2's own decision on query-params ("into the input schema") requires new zod schemas that don't exist, and Phase 2's file-scope lock forbids adding them where they'd naturally live
- **Severity:** Medium
- **Location:** Phase 2, §"Quyết định chốt tại đây" item 2; §Related Code Files "Không sửa file nào ngoài `src/lib/actions/` và `tests/`"
- **Flaw:** The plan resolves open question #2 by deciding `?q=`, `?sort=`, `?limit=` etc. belong in the action's `input` zod schema, "dùng lại validator sẵn có" style. But `src/lib/validators.ts` (grep-verified, `src/lib/validators.ts` exports only `contactInput/Patch`, `companyInput/Patch`, `dealInput/Patch`, `taskInput/Patch`, `noteInput`, `activityLogInput`) contains **no list/query-filter schema for any entity** — `contacts.list`'s input (`q`, `status`, `companyId`, `sort`, `limit`) has no existing zod definition to reuse. Someone must author it from scratch in Phase 2 (to satisfy the `tests/action-json-schema.test.ts` ground-truth requirement against MCP's existing loose `list_contacts` schema). But Phase 2's Related Code Files section states plainly: *"Không sửa file nào ngoài `src/lib/actions/` và `tests/`."* `src/lib/validators.ts` is outside that boundary.
- **Failure scenario:** The implementer either (a) inlines a duplicate list-filter zod schema inside `src/lib/actions/contacts/list.ts`, contradicting the plan's own "dùng lại validator sẵn có" reuse principle and creating a second source of truth for contact fields/enums that can drift from `validators.ts` — precisely the kind of drift this whole plan exists to eliminate — or (b) modifies `validators.ts`, silently violating Phase 2's stated file-scope constraint with no success-criterion catching it (the criterion only checks `package.json` diff, not file scope).
- **Evidence:** `grep -n "^export const" src/lib/validators.ts` → 6 schemas, none list-shaped; `plans/.../phase-02-action-kernel.md:112-116` (decision); `plans/.../phase-02-action-kernel.md:145` (file-scope lock).
- **Suggested fix:** Explicitly add `src/lib/validators.ts` (new list-filter schemas) to Phase 2's Related Code Files / Create-Modify list, and state whether list schemas live there or intentionally as a one-off inside `src/lib/actions/contacts/list.ts` (documented as a deliberate exception, not an oversight).

## Edge cases found by scout (folded into findings above)
- pg-boss enqueue uses a separate DB connection/role from the RLS request transaction — not surfaced by either phase's risk table (Finding 5).
- Workflow `runAction()` never re-enters `dispatchEvent`, so today's "infinite loop" risk is structurally absent rather than guarded — the plan treats it as an open question to check rather than reporting the actual (incidental, fragile) state (Finding 2).
- Phase 4's coverage-gate pseudocode (`expect(restRoutes).toContain(action.name)`) assumes `restRoutes`/`gqlFields`/`mcpToolNames` are readily enumerable at test time; no such introspection helper exists yet in `tests/` or `src/lib/actions/`. Not written up as a full finding (Medium-low, speculative) but worth flagging before Phase 4 starts.

## Unresolved questions
1. Should the CHANGELOG/behavior-change warning ship in Phase 1 (when the behavior actually changes) rather than Phase 4 (when it's the "consolidation" phase)? Finding 1 argues yes.
2. Does Vitest's ESM interop actually let `vi.spyOn` intercept a named import re-exported through `@/lib/workflows/engine` in this codebase? Unverified — no existing example to confirm either way (Finding 4).
3. Where should list/query-filter zod schemas live — `validators.ts` (breaks Phase 2's file-scope lock) or inline in `src/lib/actions/contacts/` (breaks the "reuse existing validator" principle)? Needs an explicit decision before Phase 2 starts (Finding 6).
